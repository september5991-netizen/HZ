# Модель доверия: первый контракт
## Реализовано
AuthenticatedPeer — внутренний результат проверенного транспортного адаптера.
TrustGrant — локальная привязка device_id к отпечатку ключа и разрешённым действиям.
evaluate_trusted_command проверяет совпадение отправителя с peer, ключом grant,
локальными правами и отзывом, затем адрес, срок и повторы через базовую политику.
Grant перечитывается для каждой команды. Неизвестный/отозванный peer отклоняется.
Данные сейчас в памяти; перезапуск, конкурентные изменения и дисковая сохранность не обеспечены.
Создать AuthenticatedPeer в Python может любой код: это граница API, не доказательство криптографии.
Нельзя строить peer из полей JSON, IP-адреса, имени устройства или заявленного отпечатка.

## Угрозы и необходимые следующие меры
- Подмена sender_id: сверка с идентичностью проверенного TLS/криптоканала.
- MITM при первом подключении: проверенный механизм сопряжения, одноразовое приглашение,
  подтверждение обоих устройств, сверка QR/кода, ограничение попыток и времени.
- Повтор команды: канонический ID плюс атомарная постоянная запись до действия.
  Привязывать ID к отправителю и содержимому; сейчас лишь переданный набор processed_ids.
- Компрометация ключа: отзыв, смена ключа через новое подтверждение, защищённое хранилище ОС.
- Устаревшие права: получатель решает по актуальной локальной политике.
  Офлайн-отзыв не распространяется мгновенно; удалённое устройство до синхронизации
  может знать старое состояние. Гарантии отзыва требуют отдельного протокола.
- Истощение ресурсов: лимиты кодека; транспортные тайм-ауты/rate limiting ещё нужны.
- Сбой после действия: durable журнал и unknown outcome; exactly-once не обещается.
- Вредоносный AI-текст: только структурированные действия через ту же политику.
- Захваченная ОС: вне гарантий проверки сообщений; модель не защищает от владельца
  процесса, изменившего grants/код, или от кражи ключа на разблокированном устройстве.

## Сопряжение и административная роль (проект, не код)
Состояния: неизвестное -> ожидает подтверждения -> доверенное -> отозванное.
Само обнаружение не выдаёт прав. Начальные права минимальны и адресны.
Перенос роли: подтверждение старого и нового администратора, версия полномочий,
атомарная фиксация и аудит. Не выбирать нового администратора автоматически при разрыве.
Потеря администратора требует отдельного восстановления владельцем; механизм ещё не определён.
Роль администратора не обходит sandbox/разрешения ОС и не выдаёт системные права автоматически.

## Возможности первого этапа
Все целевые платформы: ping/message внутри активного приложения, после реализации клиента.
Windows/Linux/macOS: системные действия только через отдельные адаптеры и права ОС.
Android/Wear OS/TV: учитывать разрешения и ограничения фонового выполнения.
iOS/iPadOS: не обещать постоянно доступный фон или произвольное управление системой.
Системные команды, VPN, голос и AI в этом этапе отсутствуют.
