# ADR 0001: протокольный каркас и границы первого прототипа

Статус: принято для текущего каркаса; транспорт и клиенты — предложения до проверки.

## Решение
Сохраняем существующий Python 3.10+ как исполняемую эталонную модель протокола.
Не переписываем каркас на Rust до проверки требований и стоимости мобильной интеграции.
JSON v1 — предполагаемый межплатформенный формат, а не Python-объекты в сети.
UUID команды принимается только в каноническом нижнем регистре с дефисами.
ping имеет пустой payload; message — только строковое поле text до 4096 символов.
Текущий Command — внутренняя модель, сетевой декодер ещё не реализован.

Разделяем protocol/domain, identity/security, transport, persistence/sync,
capabilities и UI. AI и VPN подключаются отдельными адаптерами позднее.

## Следующие границы безопасности
Идентичность определяется ключом устройства, не произвольным sender_id.
Сопряжение требует подтверждения обеих сторон и проверенного механизма привязки ключа
к QR/короткому коду. Обнаружение устройства не выдаёт доверие.
Получатель сверяет sender_id с аутентифицированным соединением и проверяет
актуальные локальные разрешения, отзыв доверия, адрес и срок каждой команды.
Администратор управляет выдачей прав, но не обходит ограничения ОС.
Передача роли требует согласия обеих сторон и версии полномочий; конфликт
или недоступность участников не создаёт нового администратора автоматически.
Полная модель угроз и матрица возможностей платформ остаются следующими документами.

Для первых двух локальных процессов предлагаем TLS с проверкой закреплённых
ключей/сертификатов и ограниченными JSON-кадрами. Конкретная библиотека и безопасное
сопряжение требуют отдельной проверки; собственного криптопротокола не создаём.
Оба устройства способны быть отправителем и получателем. Windows не обязательный сервер.
Relay позднее передаёт зашифрованные сообщения, не получает полномочий устройства.

SQLite — предлагаемая база журнала и дедупликации: резервирование ID транзакцией
до действия, привязка ID к отправителю и содержимому, сохранение результата.
accepted, executed, failed, unknown outcome — разные состояния.
Сбой между действием и фиксацией результата означает unknown outcome, а не разрешение
автоматически повторить действие. Exactly-once для произвольных действий не обещаем.
Изменённое содержимое с тем же ID отклоняется; срок хранения учитывает срок команды
и допустимое расхождение часов. Общая синхронизация отделена от локальных настроек.

## Клиенты и альтернативы
Первый Windows-клиент: минимальный Python CLI для проверки протокола.
Android: Kotlin/Compose с реализацией общего контракта и общими тестовыми векторами.
Python не объявляется встраиваемым общим runtime для iOS/Wear OS.
Rust + UniFFI остаётся кандидатом на переносимое ядро после доказательства связи.
Flutter/Kotlin Multiplatform — альтернативы общего UI/логики, требуют проверки
поддержки целевых платформ, фоновых режимов, лицензий и трудоёмкости сборки.

Для iOS/macOS — платформенные адаптеры; Wear OS/TV требуют отдельного UI.
Одинаковый системный доступ на всех ОС не обещается.
Сначала физический Android и GitHub Actions, без тяжёлого эмулятора на ноутбуке.
Секреты хранятся средствами ОС, не в Git. Защищённое хранение БД и ключей ещё не реализовано.

## Проверка и ограничения
Unit tests выполняются без сторонних Python-пакетов.
CI проверяет Windows/Linux и Python 3.10/3.12.
Валидатор не аутентифицирует отправителя, не исполняет команды, не обеспечивает
постоянную дедупликацию и не является защищённым приложением.
